  `DESIGNER /LoadExternalDataProcessorOrReportFromFiles <корневой .xml> <.epf>` (та же команда,
  что `glue.py` использует для `epf_build`, только вручную один раз для `epf_runner`).

## #24: `deploy_module` создавал модуль client+server одновременно (исправлено)
`module_deploy.py`/`_MODULE_XML_TEMPLATE` жёстко связывал ОДНИМ параметром `server` сразу оба флага:
`<Server>` И `<ClientManagedApplication>`/`<ClientOrdinaryApplication>`. Новый общий модуль
получался ОДНОВРЕМЕННО клиентским и серверным. Следствие (пойман вживую): такой модуль, вызывая ИЗ
СЕБЯ другой чисто серверный общий модуль в серверном контексте выполнения (например YaXUnit-тест
через `ДобавитьСерверныйТест`), падает с `Переменная не определена` — платформа не резолвит вызов,
хотя оба модуля в ОДНОМ расширении и вызываемый модуль реально существует и корректен. Ушло очень
много времени на ложный след "расширения не видят общие модули друг друга" (это тоже реальное
ограничение, но не было причиной в этот раз — конкретно тут модуль был в ТОМ ЖЕ расширении).
Нашёл и починил пользователь, не агент. Исправлено: `deploy_common_module`/MCP `deploy_module`
получили независимый параметр `client` (по умолчанию `False`) — НОВЫЙ модуль теперь ЧИСТО
серверный, если явно не попросить `client=True`. Если модуль ведёт себя странно с "Переменная не
определена" при вызове ДРУГОГО общего модуля — ПЕРВЫМ ДЕЛОМ проверить `Server`/`Client`-флаги
обоих модулей через `describe_metadata` или прямой запрос свойств, а не искать проблему в
расширениях/областях видимости.

## #25: `sync_extension_files` + `check_event_log` — закрывают дыры, найденные вживую
Реальная сессия тестирования #23 упёрлась в три системных пробела инструментария:

1. **Не было способа точечно поправить файл внутри расширения, кроме одноразовых Python-скриптов.**
   Дважды за сессию пришлось руками писать `subprocess`-скрипт поверх
   `DumpConfigToFiles`/`LoadConfigFromFiles`/`UpdateDBCfg` (правка `DataProcessors/.../ObjectModule.bsl`,
   удаление дубля общего модуля). Теперь это `sync_extension_files(ib_connection, ext_name, writes,
   deletes)` — универсальный, один инструмент вместо каждый раз писать новый скрипт (см. таблицу).
   `deploy_extension_from_files` (заливка ЦЕЛОГО стороннего дампа с диска) для этого НЕ годится —
   падает на несвязанном рассинхроне версии формата у нетронутых файлов (см. «Осталось»/#25 выше).

2. **Агент не видел то, что видит пользователь во всплывающих окнах 1С** (например критичное
   "Уже существует объект с именем CommonModule.Х" при дублировании модуля в двух расширениях,
   или ошибки инициализации модуля при компиляции). run_module/deploy_module такие всплывающие
   диалоги 1С:Предприятия в свой вывод не кладут вообще — по факту без скриншота от пользователя
   агент не понимал, что происходит, и тратил время на неверные гипотезы (лицензионный слот и т.п.).
   Решение — `check_event_log(minutes_back, limit)`: читает Журнал регистрации 1С через
   `ВыгрузитьЖурналРегистрации` (фильтр по `Ошибка`/`Предупреждение`). ДВЕ грабли по пути:
   - `run_module` выполняется в headless-обработке с ПРИНУДИТЕЛЬНЫМ безопасным режимом (защита от
     произвольного файлового I/O из LLM-кода). `ВыгрузитьЖурналРегистрации` как "доверенная"
     платформенная функция ЗАПИСЬ разрешает, а ЛЮБОЕ чтение файла обратно ИЗ BSL (`ЧтениеXML.
     ОткрытьФайл`, `ДвоичныеДанные(Путь)`, `ЧтениеТекста(Путь)` — ВСЕ) падает с "Установлен
     безопасный режим". Решение: BSL только пишет XML в путь внутри `runtime_dir` проекта, а
     разбирает его уже `event_log.py` (Python, `xml.etree.ElementTree`) — СНАРУЖИ песочницы 1С.
   - `Фильтр.Уровень` в `ВыгрузитьЖурналРегистрации` принимает МАССИВ значений перечисления
     `УровеньЖурналаРегистрации.Ошибка/.Предупреждение`, а НЕ строки `"Ошибка"`/`"Предупреждение"` —
     со строками фильтр молча игнорируется (выгружает вообще все уровни, включая Information), это
     выглядит как "фильтр не сработал", хотя ошибки не было — просто неверный тип значения.

3. **`lint_module`: `"ok": false` пугает, хотя код рабочий.** BSL Language Server по умолчанию
   считает `Error`-severity ряд диагностик, которые реально исполняются в 1С без проблем — например
   `MissingCodeTryCatchEx` (пустой блок `Попытка...Исключение...КонецПопытки`), а это ДЕЛИБЕРАТИВНЫЙ
   паттерн-заглушка, используемый по всему проекту `vkr_`. Увидев `ok: false`, агент один раз решил,
   что модуль сломан, хотя единственная реальная проблема была ДРУГАЯ (незакрытый `#Область`).
   Исправлено: `tools/bsl-language-server.json` (флаг `-c` в `bsl_ls.py`) понижает
   `MissingCodeTryCatchEx` до `Information` — диагностика остаётся в выводе (не скрыта), просто не
   роняет итоговый `ok`. При разборе `diagnostics` смотреть на конкретный `code`+`severity`, а не
   только на итоговый `ok` — там ещё много `Information`/`Hint`/`Warning` находок стиля/сложности,
   они НЕ блокируют выполнение и не требуют немедленной правки.

4. **`kill_sessions`/`protect_interactive` не признавал `RunUnitTests` "своим".** Изначально
   `_is_automation_process` (см. `sessions.py`) распознавал только `/Execute` (форма-раннер) —
   зависшую headless-сессию `ENTERPRISE .../C"RunUnitTests=..."` считал "интерактивной" и не
   закрывал, пользователю приходилось закрывать её вручную. Исправлено — маркер `rununittests=`
   добавлен в распознавание.

5. **MCP-таймаут клиента короче реальных DESIGNER/ENTERPRISE-операций на тяжёлой ERP-конфигурации.**
   `deploy_module`/`run_tests` на большой конфигурации (в этой сессии — 1С:ERP АПК) регулярно уходят
   в клиентский timeout ДОЛЬШЕ, чем ждёт MCP-клиент, при этом СЕРВЕРНЫЙ процесс продолжает работать
   в фоне и рано или поздно завершается сам. Это НЕ означает сбой — правильная реакция: проверить
   `list_sessions()`, и если процесс ещё жив — подождать (не повторять вызов вслепую, повторные
   вызовы поверх ещё выполняющегося создают гонки и дублирующиеся DESIGNER-процессы на одну и ту же
   папку `runtime/ext_src/<ext>`, что однажды привело к повреждённому XML — см. урок про
   одновременные вызовы ниже).
6. **Одновременные/повторные вызовы `deploy_module` в ОДНУ И ТУ ЖЕ папку `runtime/ext_src/<ext>`
   могут повредить промежуточные файлы** (гонка между "ещё пишущимся" от предыдущего вызова и новым
   `DumpConfigToFiles`). Если видите на клиенте таймаут — НЕ повторяйте вызов сразу; сначала
   `list_sessions()`, дождитесь исчезновения DESIGNER-процесса, при сомнении — очистите
   `runtime/ext_src/<ext>` перед повтором (`created: false` вместо ожидаемого `true` при заведомо
   новом объекте — верный признак, что подхватился стейл-кэш, а не свежий дамп из БД).
7. **Перенос общего модуля из одного расширения в другое — ОБЯЗАТЕЛЬНО удалить старую копию.**
   Если тестовый/бизнес-модуль сначала создан в расширении А, а потом решено, что ему место в
   расширении Б (например, из-за #24 выше) — простое `deploy_module` в Б НЕ убирает копию в А.
   Итог — дублирующееся имя `CommonModule.Имя` в двух расширениях, конфигурация валится с критичной
   ошибкой при инициализации ("Уже существует объект с именем..."), которую видно ТОЛЬКО во
   всплывающем окне 1С (см. пункт 2 выше) или через `check_event_log`. Удаление старой копии теперь
   тривиально: `sync_extension_files(ib_connection, ext_name=А, deletes=["CommonModules/Имя.xml",
   "CommonModules/Имя"])` — сам уберёт и файлы, и тег из `Configuration.xml`.

## #26: async job_id/job_status для деплоя + describe_common_module + lock + дубли (завершено)
Продолжение #25 — ещё 4 доработки инструментария по итогам той же сессии тестирования:

1. **`deploy_module`/`sync_extension_files`/`deploy_extension_from_files`/`run_tests` теперь
   АСИНХРОННЫЕ** — тот же паттерн `_spawn`/`_JOBS`/`job_status`, что уже был у `heal_module`/
   `fix_snippet`. Раньше эти 4 инструмента были синхронными и регулярно упирались в клиентский
   MCP-таймаут на тяжёлой ERP-конфигурации (см. #25 п.5) — агент не мог отличить "зависло" от
   "просто медленно" и был вынужден вручную опрашивать `list_sessions()`. Теперь вызов возвращает
   `job_id` мгновенно, результат — `job_status(job_id)`. ВАЖНО: внутренние `timeout` в
   `module_deploy.py`/`extension_deploy.py`/`yaxunit_runner.py` подняты с 60-180с до 600с — иначе
   фоновый поток сам обрубал бы DESIGNER-процесс на середине операции (subprocess.run(timeout=...)
   убивает дочерний процесс по истечении), просто сдвинув ту же проблему с клиента на сервер.

2. **`job_status` стал событийным** — новый параметр `wait_seconds` (по умолчанию 0 = старое
   мгновенное поведение). При `wait_seconds > 0` блокируется на `threading.Event` до завершения
   задачи, но НЕ дольше `min(wait_seconds, 55)` — потолок специально ДЕРЖИТСЯ ПОД клиентским
   MCP-таймаутом, чтобы сам `job_status` не подвис так же, как раньше зависали синхронные вызовы.
   Возвращается СРАЗУ по завершении (не ждёт полный wait_seconds, если задача готова раньше) —
   закрывает жалобу "почему ты ждёшь ScheduleWakeup вслепую вместо того, чтобы продолжить, как
   только проверка реально закончилась".

3. **`describe_common_module(module_name)`** — Server/Client/ВызовСервера/Привилегированный-флаги
   существующего общего модуля (`Метаданные.ОбщиеМодули.Найти`). Появился напрямую из-за #24 —
   с этим инструментом баг нашёлся бы за секунды, а не за долгий ложный след. Подтверждённые вживую
   имена свойств: `Глобальный`, `Сервер`, `ВнешнееСоединение`, `КлиентУправляемоеПриложение`,
   `КлиентОбычноеПриложение`, `ВызовСервера`, `Привилегированный`.
   **Побочная находка при юнит-тесте парсера:** `metadata_tool._TS_RE` (regex среза временнОй метки
   `"дд.мм.гггг чч:мм:сс: "` перед первой строкой лога) требовал РОВНО 2 цифры часа (`\d{2}`), а
   1С не дополняет час нулём ("4:56:55", не "04:56:55") — метка НЕ срезалась примерно 40% времени
   суток (час 0-9), портя первую строку разбора у ВСЕХ парсеров через `_strip_ts` (`describe_metadata`
   census/index/detail, `query_data`). Исправлено на `\d{1,2}`. Баг мог тихо искажать результаты
   этих инструментов и раньше — просто не был замечен, если начало строки визуально выглядело
   "почти правильно".

4. **Best-effort проверка дублей имени модуля** — `deploy_module` при создании НОВОГО модуля
   (created=True) сканирует уже закэшированные `runtime/ext_src/<другое_расширение>/CommonModules/
   <Имя>.xml` и кладёт `duplicate_warning` в результат, если то же имя уже встречалось в ДРУГОМ
   расширении (не блокирует деплой — только предупреждает; не исчерпывающе, не сканирует
   расширения, которые ни разу не дампились на этой машине/сессии). Прямая защита от повторения
   #25/п.7 (дубль `CommonModule.Имя` в двух расширениях).

5. **`dump_lock(dump_dir)`** (`dump_lock.py`) — `.lock`-файл (`<pid>|<unix-время>`, проверка через
   `tasklist`) вокруг Dump/Load/Update в `deploy_module`/`sync_extension_files` (НЕ в
   `deploy_extension_from_files` — там `ext_root` внешний путь пользователя, не наша managed-папка,
   гонка неактуальна). Протухший лок (процесс мёртв или старше 600с) снимается сам, живой — кидает
   понятную ошибку вместо молчаливой порчи файлов (см. #25 п.6).

**Честная граница, найденная при живой проверке:** автоправка тега `<CommonModule>Имя</CommonModule>`
в `Configuration.xml` (и при создании в `deploy_module`, и при удалении в `sync_extension_files`)
использует ПРОСТОЕ совпадение строки, не XML-парсинг. При живой проверке удаление реального модуля
дало `tag_warnings: "тег не найден (уже отсутствовал?)"`, хотя модуль был создан именно через
`deploy_module` (то есть тег ДОЛЖЕН был добавиться) — при этом `LoadConfigFromFiles`/`UpdateDBCfg`
всё равно отработали корректно, и итоговый `Configuration.xml` НЕ содержал никакой ссылки на
удалённый модуль (проверено `grep` по свежему дампу) — то есть 1С сама корректно поддерживает
ChildObjects при пересборке из файлов, и промах точного строкового совпадения в эту конкретную
секунду не привёл к реальной порче конфигурации. Тем не менее `tag_warnings` может врать в обе
стороны (ложное "не найдено") — доверяйте общему `ok`/факту успешного `UpdateDBCfg` и при сомнении
проверяйте реальный `Configuration.xml`, а не только `tag_warnings`.

Все 5 пунктов проверены вживую (не только compile-check): `describe_common_module` — на реальном
`vkr_Операции` (найден+не найден), `check_event_log` уже был проверен в #25, `deploy_module`+
`job_status` — на новом тестовом модуле (job завершился, `created:true`, без дублей), `run_tests`
асинхронно — 10/10 зелёных с новым тестом, `sync_extension_files` — модуль корректно удалён
(итоговый прогон снова 9/9).

## #27: verify_extension — составной пайплайн (завершено)
Один инструмент вместо ручной склейки того, что агент делал шаг за шагом ВСЮ сессию
тестирования vkr_ (#23-26): `lint_module` по каждому `*.bsl` из `writes` → (если что-то
реально передано) `sync_extension_files` → поднять форму-раннер (ТОЛЬКО если для этой
базы ещё нет живой — проверка по `/Execute` в CommandLine, не плодит параллельные
сессии) → `run_tests` → `check_event_log`. Один результат:
`{"stages": {...}, "verdict": "ok"|"lint_failed"|"deploy_failed"|"test_failed"|"needs_review"}`.

Без `writes`/`deletes` — режим "просто проверить текущее состояние живой базы", деплой
пропускается. `lint_failed` останавливает пайплайн ДО касания живой БД — не тратим
дорогой деплой на заведомо нерабочий код. Реализация — `verify.py`, регистрация как
асинхронный инструмент (`job_id`/`job_status`) в `mcp_server.py`.

Проверено вживую end-to-end дважды: (1) с валидным (но пустым — линт не блокирует)
новым `.bsl`-файлом → `verdict: "ok"`, все 5 стадий заполнены, `event_log` честно
показал 20 НЕСВЯЗАННЫХ старых ошибок фонового задания ERP (не отфильтровывает "свои"
события от чужих — весь актуальный журнал); (2) чистка мусора через
`sync_extension_files` deletes — тот же паттерн `tag_warnings` "не найдено" из #26,
воспроизведён третий раз (стабильно, не случайность) — тег никогда и не создавался,
так как `sync_extension_files.writes` намеренно НЕ регистрирует новый общий модуль в
`Configuration.xml` (это работа `deploy_module`), поэтому предупреждение здесь
ожидаемо корректное, а не баг.

**По ходу отдельно прояснили природу `warmup()`** (`Real1CRunner.warmup`): это НЕ
отдельный механизм, а буквально `run_module()` с зашитым тривиальным кодом
(`ЛогВыполнения = "ГОТОВО"`). Смысл — не "прогрев" на уровне нашего кода, а дешёвый
предсказуемый способ проверить, что сессия/пайплайн вообще живы, не тратя на это

## #34: разгадан "невидимый функциональный баг" форм из ретро-билета №15 (завершено)
Ретроотчёт по билету №15 фиксировал единственную находку, прошедшую ВСЕ
автоматические проверки (XML-валидация + LoadConfigFromFiles/UpdateDBCfg без
ошибок) и пойманную только пользователем вручную в реальном клиенте: клиентский
пересчёт Суммы по `Event name="ПриИзменении"` на поле ТЧ не срабатывал.
Причина найдена пользователем: назначил обработчик через РЕАЛЬНЫЙ Конфигуратор
(свойство поля "При изменении"), выгрузил `Form.xml` — формат оказался ДРУГИМ,
чем зафиксированный в `get_guide("main_config_forms")` после #33:
1. Тег события должен быть ВЛОЖЕН в контейнер `<Events>`, а не быть прямым
   сиблингом `DataPath`/`EditMode`/`ContextMenu` внутри `InputField`.
2. Атрибут `name` — ВНУТРЕННИЙ английский идентификатор события платформы
   (`OnChange`), а НЕ русское имя события из палитры свойств (`ПриИзменении`).
   Платформа хранит события под английскими идентификаторами независимо от
   языка интерфейса — русское имя `ПриИзменении`, использованное в #33, было
   похоже на настоящее событие только по написанию имени ПРОЦЕДУРЫ
   (`ТоварыЦенаПриИзменении`), а не по значению атрибута `name`.

Правильный формат:
```xml
<InputField name="ТоварыКоличество" id="18">
    <DataPath>Объект.Товары.Количество</DataPath>
    <EditMode>EnterOnInput</EditMode>
    <ExtendedEditMultipleValues>true</ExtendedEditMultipleValues>
    <ContextMenu name="ТоварыКоличествоКонтекстноеМеню" id="19"/>
    <ExtendedTooltip name="ТоварыКоличествоРасширеннаяПодсказка" id="20"/>
    <Events>
        <Event name="OnChange">ТоварыЦенаПриИзменении</Event>
    </Events>
</InputField>
```
`get_guide("main_config_forms")` исправлен — старый (неверный) вариант оставлен
в тексте гайда явно помечен как ГРАБЛЯ/НЕ РАБОТАЕТ, рядом с рабочим, чтобы не
повторить выбор неверного варианта по памяти. **Общий вывод для инструмента**:
"LoadConfigFromFiles/UpdateDBCfg прошли без ошибок" НЕ равно "семантически
верно" — этот урок уже был сформулирован в общем виде в ретроотчёте по билету
№15 (раздел "XML синтаксически валиден, но семантически не то"), теперь есть
конкретный подтверждённый пример для форм в дополнение к Subsystem/DCS-parameter
из #32/#33. Живая база TestDB15 (`runtime/config_src/TestDB15/.../Form.xml`)
уже содержит исправленный формат — правка сделана пользователем напрямую через
Конфигуратор, откатывать/передеплоивать не требуется.

**Открытый риск, который это НЕ закрывает**: для проверки формата события
понадобился человек, кликающий в реальном Конфигураторе — агент не может
самостоятельно проверить, что обработчик СРАБАТЫВАЕТ в клиенте (только что XML
грузится без ошибки). Пока нет способа автоматически тестировать интерактивное
поведение формы (клик/ввод/визуальный пересчёт) без GUI-доступа человека — см.
идею `screenshot_1c_window()` ниже, но она читает СТАТИЧНЫЕ диалоги/окна, а не
симулирует пользовательский ввод в живую форму, так что эту границу не снимает.

MCP-инструмент — тому нужен был бы `sync_main_config_files`, которого пока
нет). Результат: `"Обновление конфигурации успешно завершено"`

сравнение показало `<Form>` на глубине 5 вместо ожидаемой 3. Исправлено:
якорь патча теперь `"\n\t\t</ChildObjects>"` (с ведущим `\n`) — однозначно
матчит только строку, которая НАЧИНАЕТСЯ РОВНО с 2 табов, не суффикс более
глубокой строки. После фикса — глубина `<Form>` совпадает с реальным файлом
(3), полное совпадение набора тегов.

**Идемпотентность подтверждена**: патч на РЕАЛЬНОМ `ПриходнаяНакладная.xml`

`Attribute→TabularSection→Form`). Для КОРНЕВОГО `Configuration.xml`
`ChildObjects` порядок подтверждённо НЕ важен (см. `main_config_internal_

порядок КРИТИЧЕН — см. #32), НЕ отдельно подтверждённый факт. Не

  Managed`, БЕЗ `ChildObjects` вообще.
- `Ext/Form.xml` содержит ДВЕ копии структуры формы: внешнюю (правки
  расширения) и вложенную `<BaseForm version="2.19">` — НЕТРОНУТЫЙ снимок

параметр `child_forms` (рендерит непустой `ChildObjects` вместо
самозакрывающегося); `build_adopted_form_descriptor_xml`; `build_borrowed_form_xml`

вёрстку — только оборачивает в `BaseForm` и патчит `Action` уже существующих
команд по имени через regex, `ValueError` если команда не найдена, силой не
угадывает); `adopt_form` — полный пайплайн (dump→документ Adopted с

заимствован→kill→load→update, всё `-Extension`). `_FORM_NS` (namespace-блок

## #53: logs.txt — предохранитель от неограниченного роста (завершено)
Пользователь заметил, что при каждом прогоне Claude как будто читает лишние
тысячи старых строк из `work/logs.txt`. Разбор `glue.Real1CRunner.__call__`
показал: сам механизм дельты (байтовый оффсет `before`/`logs.read_bytes()
[before:]`) УЖЕ отдаёт наружу только вывод ТЕКУЩЕГО прогона — если Claude
видел лишнее, это был прямой `Read` файла в обход механизма (уже
задокументированный антипаттерн, см. "Уроки"), не баг дельты.

НО нашлась РЕАЛЬНАЯ, независимая проблема: BSL-процедура `ЗаписатьВЛог`
(`ВнешняяОбработкаИИАгент/Forms/Форма/Ext/Form/Module.bsl`) на КАЖДУЮ запись
читает `logs.txt` ЦЕЛИКОМ (`ТекстовыйДокумент.Прочитать`), добавляет одну
строку и перезаписывает файл ЦЕЛИКОМ обратно — O(текущий_размер) на вызов,
без всякого предохранителя. Отсюда и неограниченный рост файла, и
постепенное удорожание каждого прогона по мере роста истории проекта.

**Фикс — ТОЛЬКО на Python-стороне** (`glue.py`, `Real1CRunner._LOGS_MAX_BYTES
= 200_000`): перед каждым прогоном, если `logs.txt` превысил лимит, файл
обрезается до последних 200КБ. BSL-код НЕ тронут — не хотели гадать точную
сигнатуру `ЗаписьТекста`/режим добавления в конец без возможности проверить
живьём (та же осторожность, что и с любым новым форматом весь этот проект).

**Важная тонкость, которую пришлось продумать (гонка с дельтой):** обрезка
сделана СТРОГО ДО того, как в `__call__` считается `before = logs.stat().
st_size` — если бы обрезка происходила ВНУТРИ самого BSL-вызова (между тем,
как Python запомнил `before`, и тем, как прочитал `[before:]` после), `before`
мог бы указывать ЗА пределы нового (уже обрезанного) размера файла — тогда
срез `[before:]` в Python тихо вернул бы ПУСТУЮ строку вместо реального
вывода прогона, что сломало бы `parse_1c_errors`/весь `heal()`. Гонки с самим
BSL нет: в момент обрезки раннер простаивает (ждёт "WAIT"), логи никто не
пишет. Проверено симуляцией последовательности (truncate → append → delta-
read) — оффсет остаётся консистентным.

## #54: семантический поиск по процедурам эталонного корпуса (embeddinggemma-300M)

**Реальные цифры корпуса (посчитаны, не угаданы):** 25774 BSL-файла, 788.5
млн символов кода, **642669 процедур/функций всего**, из них **209188

**Решение индексировать ВСЁ, не только Экспорт** (обсуждено с пользователем,

пустую обёртку, вся суть осталась бы невидимой. Минус закрытых — у них реже
doc-комментарий, но само имя процедуры на русском обычно осмысленное.

**Почему НЕ векторная СУБД** (тоже пересчитано после честной ошибки — сначала
сказал "мало векторов", это было неверно): 642669 векторов размерности 768 —
это ~2ГБ float32, НЕ мало, но специализированный движок (Milvus/Qdrant)
оправдан от десятков МИЛЛИОНОВ векторов или для конкурентной серверной
выдачи — ни то ни другое не применимо к одному локальному Python-процессу.

## #56: живой тест /IBName — нашлись СРАЗУ ТРИ реальных бага (завершено)

Пользователь открыл 1С через штатный "Список информационных баз" (НЕ через
сырой путь) — реальная база `File="C:\Users\danua\Documents\InfoBase24";`,
отображаемое имя в списке — "Информационная база". `list_sessions(ib_connection=
...)` вернул ПУСТО — матчинг не сработал ВООБЩЕ, хотя #45 п.6 был помечен
"реализовано". Раскопки нашли ТРИ независимых реальных бага, ни один не
был бы найден без реальной живой 1С:Стартер-сессии:

**Баг №1 — `_IBNAME_RE` требовал пробел, которого в реальности нет.**
Регэксп был `r'/IBName\s+"([^"]+)"|/IBName\s+(\S+)'` (обязательный `\s+`).
Реальная командная строка процесса: `/IBName"Информационная база"` —
БЕЗ пробела между `/IBName` и открывающей кавычкой. Исправлено на
`/IBName\s*"([^"]+)"` (`\s*`, пробел опционален) для кавычечного варианта.

**Баг №2 — кодировка вывода PowerShell.** `_run_ps()` захватывал
`subprocess.run(..., text=True)` — Python декодирует через LOCALE-кодировку,
на этой машине это НЕ то, чем PowerShell реально пишет перенаправленный
stdout. Экспериментально перебраны cp1251/cp866/utf-8/utf-16 на СЫРЫХ
байтах реального вызова — верно декодировал ТОЛЬКО `cp866` (OEM-кодовая
страница консоли), подтверждено программным сравнением строк (`"Информационная
база" in text`), не визуально на глаз (в терминале кириллица всё равно
искажается при выводе — на это полагаться нельзя, только на сравнение).
Без этого фикса вся кириллица в `CommandLine` (включая имя базы после
`/IBName`) превращалась в мусор — `_IBNAME_RE` находил "имя", которого
не было ни в одном реестре ibases.v8i, поэтому ничего не резолвилось.

**Баг №3 — резолв имени терял правильный вариант при коллизии между
профилями.** На машине пользователя ДВА профиля 1С:Стартер (`1CEStart`/
`1CEStartt`, см. #45 п.6 — уже было известно, что профилей несколько). В
ОБОИХ оказалась запись с ОДИНАКОВЫМ именем "Информационная база", но
указывающая на РАЗНЫЕ реальные пути (`InfoBase24` в одном профиле,
`InfoBase22` — в другом, случайно оставшаяся старая запись). `_load_ibase_
registry()` хранил ОДНО значение на имя — второй прочитанный профиль молча
перезаписывал первый, и матчинг резолвил `/IBName` в СОВЕРШЕННО ДРУГУЮ базу,
чем реально была открыта. Исправлено: реестр теперь `{имя: [список
вариантов]}`, `_matches` проверяет совпадение С ЛЮБЫМ из вариантов, а не
только с последним "выигравшим" при перезаписи.

**После всех трёх фиксов — подтверждено вживую end-to-end** (в обход
устаревшего MCP-сервера, напрямую через `sessions.find_matching_processes`):
`ib_connection='File="C:\\Users\\danua\\Documents\\InfoBase24";'` корректно
находит ИМЕННО тот процесс (`/IBName"Информационная база"`), который
пользователь реально открыл через список баз.

**Урок:** структурная сверка/py_compile НЕ ловят ни один из этих трёх багов
(все три — про то, как РЕАЛЬНАЯ Windows-система в РЕАЛЬНОЙ локали отдаёт
данные, а не про синтаксис/структуру кода) — ещё одно подтверждение, почему
"#45 закрыто, но не протестировано живьём" в HANDOFF корректно держалось
как отдельный статус, а не как "готово".

install.ps1", без какого-либо стороннего зеркала.

**Найдено и исправлено 4 реальных бага живым прогоном на машине автора**
(ни один не поймать без реального запуска в реальном Windows-окружении):

1. **UTF-8 БЕЗ BOM ломает PowerShell 5.1 на кириллице** — 12 ошибок парсинга
   при первой же проверке (`[System.Management.Automation.Language.Parser]::
   ParseFile`). Файл пересохранён с BOM (`utf-8-sig`).
2. **Сортировка версий Java/платформы 1С по ИМЕНИ ПАПКИ ненадёжна в принципе**
   — на машине автора реально ДВЕ версии платформы (8.3.24/8.3.26) и куча
   JDK/JRE вперемешку (jdk-11, jdk-11.0.0.1, jdk-19, jdk-21.0.8, jdk-26.0.1,
   javafx-sdk-22.0.1, jre1.8.0_51). Без сортировки Get-ChildItem вернул
   jdk-11 первым; "исправление" сортировкой ИМЕНИ строкой в обратном порядке
   оказалось ЕЩЁ ХУЖЕ — выбрало jre1.8.0_51 (Java 8, JRE не JDK), потому что
   "jre..." > "jdk-26..." лексикографически ('r' > 'd'). Единственный надёжный
   способ — реально спросить каждый `java.exe -version` и сравнить настоящие
   номера версий, не имена папок.
3. **`$ErrorActionPreference = "Stop"` + `2>&1` на нативном exe молча душит
   ошибку.** `java -version` пишет в stderr; PowerShell 5.1 заворачивает
   КАЖДУЮ строку stderr нативного процесса в ErrorRecord при `2>&1` — с
   глобальным `$ErrorActionPreference = "Stop"` это ЗАВЕРШАЮЩЕЕ исключение,
   которое пустой `catch {}` проглатывал без единого сообщения — функция
   версии молча возвращала 0 для ЛЮБОЙ реальной java.exe. Обход — прогнать
   через `cmd /c "... 2>&1"`: слияние потоков происходит НА УРОВНЕ cmd.exe,
   PowerShell видит уже обычный текст, не ErrorRecord.
4. **`lms get "owner/repo"` (короткая форма) падает на ОБЕИХ моделях.** `lms
   get` без полного URL ищет по СОБСТВЕННОМУ каталогу "staff picks" LM
   Studio, не в Hugging Face напрямую — `"qwen/qwen2.5-coder-7b-instruct"` и

   artifact... does not exist or you do not have permission". Нужен ПОЛНЫЙ
   URL (`https://huggingface.co/Qwen/Qwen2.5-Coder-7B-Instruct-GGUF` и
   аналогично для embeddinggemma) — с ним `lms get` резолвит корректно И
   распознаёт уже скачанное ("Model already downloaded"), не перекачивает.

**Реализовано:** `install.ps1` (корень проекта) — детект платформы 1С/
эталонной конфигурации/Java (с реальной проверкой версии), скачивание

## #60: автозапуск ИИ-моделей вместе с сервером (завершено, backend=lmstudio)

Закрытие незавершённого куска: `install.ps1` (#57-59) ставил модели, но их
ЗАПУСК вместе с сервером (исходный запрос — "чтобы модели запускались на

реализованным.

**Конфиг** (`config.py`): `MODEL_BACKEND` ("auto"/"lmstudio"/"llama_server"),
`AUTOSTART_FIXER_MODEL`/`AUTOSTART_EMBED_MODEL` (bool, по умолчанию `True`),

при импорте config.py (просто `Path(...).exists()` для `lms.exe`/
`llama-server.exe`, дёшево) — `FIXER_MODEL_BASE_URL`/`EMBED_MODEL_BASE_URL`
считаются от результата: при `lmstudio` ОБА на одном порту (LM Studio сама
держит несколько моделей одновременно — подтверждено вживую в #54), при
`llama_server` — эмбеддингам СВОЙ порт (один процесс = одна модель).

**Рефактор без циклического импорта:** `LM_KEY`/`LM_BASE` были захардкожены
в `fixer.py`, `embeddings_client.py` импортировал их ОТТУДА — теперь ОБА

(`find_1c_platform` и т.п.), обратный импорт дал бы цикл
`config→bootstrap→fixer→config`. `ensure_models_running(cfg: dict)` работает
ТОЛЬКО через параметр `cfg`, как и весь остальной проект — HTTP/subprocess
напрямую, без переиспользования HTTP-хелперов fixer.py.

**Реализовано** (`bootstrap.py`): `_ensure_lmstudio(cfg)` —
`lms server start` → `lms ps` (что уже загружено) → `lms load <ключ> -y`
ТОЛЬКО для того, чего ещё нет в списке загруженных (идемпотентно, не
перегружает то, что и так работает). `_ensure_llama_server(cfg)` —
для backend без LM Studio: проверка `/health` на нужном порту, если не
отвечает — `subprocess.Popen` (НЕ `run` — не блокирующий, модель может
докачиваться минуты, весь MCP-сервер не должен зависать на старте) с
`llama-server.exe -hf <repo> -p <порт> ...`. `ensure_models_running(cfg)` —
верхнеуровневая обёртка, best-effort, НИКОГДА не бросает исключение наружу
(if AUTOSTART оба выключены — no-op). Подключено в `mcp_server.py`: вызов
ДО `mcp.run()`, обёрнут ЕЩЁ одним `try/except` снаружи (двойная страховка —
падение автозапуска моделей не должно ронять весь MCP-сервер).

**НЕ протестировано, честно:** `_ensure_llama_server` (backend="llama_server")
— та же причина, что и у `install.ps1` #57-59: на машине автора LM Studio
уже стоит, эта ветка никогда не выбирается через `_detect_model_backend()`
