# 1С-агент — бриф для новой сессии Claude

## Что это
Claude-в-чате = дирижёр: пишет BSL и через MCP-сервер `1c-agent` гоняет/чинит код в **живой 1С**,
пишет/подключает расширения, гоняет YaXUnit-тесты. Локальная Qwen2.5-Coder-7B — дешёвый
микро-починщик синтаксиса (нужен только двум инструментам, см. ниже). Цель — универсальный
инструмент вайб-кодинга под 1С; юнит-тесты нужны не ради TDD-пуризма, а чтобы Claude не
перезатирал свои же проверки каждую итерацию и мог свериться, что старый функционал не сломан.

## Правило: решил новый случай вручную — оформи как инструмент
Если пришлось руками разбирать формат (DumpConfigToFiles/XML/новый вид объекта и т.п.) для задачи,
которую `deploy_module`/существующие инструменты не покрывали — задача считается закрытой ТОЛЬКО
после того, как: 1) паттерн зафиксирован в `guides.py` (новая тема), 2) написан инструмент по
аналогии с `module_deploy.py`, если случай будет повторяться. Не останавливаться на «один раз
руками сработало» — так следующий чат снова потратит 15+ минут на то же самое.

## Быстрый старт (сделай это, не спрашивая)
1. `check_setup()` — что реально есть на диске (path_1c/java/jar/cfe/epf_runner/screenshot/ocr).
   Если чего-то не хватает — это разовая ручная установка человеком, не твоя задача чинить
   автоматически.
2. Если человек продиктовал в чате строку подключения к базе (`File="...";` или
   `Srvr="...";Ref="...";Usr="...";Pwd="...";`) — используй её ЯВНО в каждом вызове,
   требующем `ib_connection`. Никогда не бери путь базы из `config.py` — там его нет специально.
3. Смотря что нужно делать — см. таблицу инструментов ниже, группа A или B.
4. Перед первым написанием тестового модуля YaXUnit — `get_guide("yaxunit_tests")` (там всё:
   регистрация тестов, ассерты, грабли тестовых данных). Не читай его, если сейчас не пишешь тесты.

## Уроки, которые всё ещё актуальны (не переоткрывать)
- **НЕ читать `work/logs.txt` напрямую через Read** — это СЫРОЙ кумулятивный лог ЗА ВСЮ историю
  прогонов. `Real1CRunner`/`run_module`/`heal_module`/`warmup` УЖЕ вычисляют и возвращают именно
  ДЕЛЬТУ этого лога за конкретный вызов в поле `output` результата.
- **#53: `Real1CRunner.__call__` теперь ОБРЕЗАЕТ `logs.txt` до последних 200КБ ПЕРЕД каждым
  прогоном**, если файл вырос больше лимита (`_LOGS_MAX_BYTES`) — найдено по вопросу пользователя:
  BSL-сторона (`ЗаписатьВЛог` в форме раннера) на каждую запись читает+перезаписывает файл
  ЦЕЛИКОМ (`ТекстовыйДокумент.Прочитать`+`Записать`), без предохранителя это O(n²) за жизнь
  проекта. Обрезка — НА PYTHON-СТОРОНЕ и СТРОГО ДО того, как посчитан `before` (байтовый оффшет
  для дельты) — если бы BSL сам обрезал файл ПОСЕРЕДИНЕ прогона, `before` мог бы оказаться больше
  нового размера файла, и срез `[before:]` тихо вернул бы пустоту вместо реального вывода. BSL-код
  НЕ трогали (не хотели гадать сигнатуру `ЗаписьТекста` вслепую) — фикс полностью на Python.
- **BSL-грабли:** `Знач` — зарезервированное слово, нельзя как имя переменной. Индексации
  `СтрокаТаблицы["Колонка"]` не существует — только `.Получить(ИндексКолонки)` (числовая индексация
  коллекций `ТЗ.Колонки[Индекс]` — работает). Динамическое имя объекта метаданных —
  `Метаданные.<Вид>.Найти(Имя)`.
- **`ЮТест.Данные().СоздатьДокумент(...)` возвращает Ссылку** — её ТЧ только на чтение,
  `.Добавить()` кидает «Объект недоступен для изменения». Для заполнения ТЧ — `КонструкторОбъекта`
  (см. `get_guide("yaxunit_tests")`).
- **`epf_build` ≠ `epf_runner`** (см. `config.py`) — headless-обработка для компиляции и форма с
  таймером — РАЗНЫЕ файлы с разными объектами 1С. Не сливать в один путь.
- **Передача пути в форму через `/C` + `ПараметрЗапуска`** — рабочий и переиспользуемый паттерн:
  если раннер запускает Python и Python каждый раз точно знает актуальный путь, не нужно ничего
  хардкодить ни в BSL, ни в файлах-маячках — просто передать значение в командной строке запуска
  и прочитать `ПараметрЗапуска` в `ПриОткрытии`/обработчике. `/Execute` и `/C` спокойно сочетаются.
- **Редактирование готового `.epf` без EDT:** `DESIGNER /DumpExternalDataProcessorOrReportToFiles
  "<outdir>" "<file.epf>" /Out <log>` — распаковка в XML+BSL. Обратно —
  `/LoadExternalDataProcessorOrReportFromFiles "<корневой .xml>" "<file.epf>"`.
- **`DESIGNER /LoadConfigFromFiles` + `/UpdateDBCfg` — ВСЕГДА раздельными вызовами subprocess**, не
  чейнить через `;` в одной команде — однажды воспроизведено вживую, что чейн закатывает старое
  содержимое модуля без ошибки в логе. Пустой `/Out`-лог не значит успех сам по себе —
  ориентируйтесь на returncode, при сомнении — перепроверка повторным `DumpConfigToFiles`.
- **`UpdateDBCfg` на файловой базе требует монопольного доступа** — если сессия (форма-раннер)
  открыта, сначала `kill_sessions`. Штатный `ЗавершитьРаботуПользователей` не годится — требует
  подсистему БСП в конфигурации, которой в лёгких базах нет.
- **DESIGNER-изменения не подхватываются уже открытой сессией 1С:Предприятия** — после
  `attach_extension`/`deploy_module` нужен `start_runner`/`restart_runner` заново для группы A.
- **`/IBName`-сессии** (клиент открыт из списка баз, не сырым `/F`/`/S`) МАТЧАТСЯ, ПОДТВЕРЖДЕНО
  живьём (#45 п.6 реализация -> #56 живой тест нашёл и исправил 3 РЕАЛЬНЫХ бага: regex без
  пробела, неверная кодировка вывода PowerShell (`cp866`, не `text=True`), коллизия имён между
  ДВУМЯ профилями 1С:Стартер — см. HANDOFF_ARCHIVE.md #56 за подробностями). Если резолв всё же
  не сработал (совсем нестандартный путь профиля) — `list_sessions()` без параметра всё ещё
  покажет все процессы глазами, гасить по PID.
- **Несколько JDK на машине** — не трогать системный PATH, указывать конкретный `java_exe`.
- **Безопасный режим расширения** — жёсткая песочница для кода САМОГО расширения, её нельзя снять
  вызывающим кодом (`УстановитьБезопасныйРежим` не поможет) — снимается только руками в
  Конфигураторе. НО можно снять программно через `РасширенияКонфигурации.Получить()...
  .БезопасныйРежим=Ложь...Записать()` (проверено вживую) — не обходить это без прямой просьбы
  пользователя (см. HANDOFF_ARCHIVE.md #32 п.4 про то, что для отключения `Активно` обходного
  пути через файлы/CLI нет вовсе — `run_module` сам в принудительном безопасном режиме).
- **Формат XML: "загрузилось без ошибки" ≠ "семантически верно".** Три подтверждённых случая
  (Subsystem #32, DCS `<parameter>` #33, `Event name="OnChange"` вместо `"ПриИзменении"` в формах
  #34) — LoadConfigFromFiles/UpdateDBCfg проходят чисто, а платформа либо не видит объект в
  интерфейсе, либо тихо возвращает 0 строк, либо клиентский обработчик просто не срабатывает.
  **Правило эскалации** (формализовано также в `get_guide("main_config_overview")`): формат
  НОВОГО вида XML-узла угадан неверно 2 раза подряд — не гадать третий раз, просить у пользователя
  реальный пример через Конфигуратор + дамп (`dump_main_config`/`dump_extension`).
- **ОБНОВЛЕНИЕ существующего объекта основной конфигурации через deploy_catalog/deploy_document/
  deploy_accumulation_register/deploy_information_register/deploy_subsystem/deploy_chart_of_accounts/
  deploy_accounting_register/deploy_report ДОЛЖНО сохранять существующий uuid/TypeId/ValueId**
  (см. `metadata_deploy._preserve_existing_ids`, #42) — платформа отслеживает объекты ПО UUID, не по
  имени; новый случайный uuid у уже существующего (по имени) объекта воспринимается как "удалить
  старый + создать новый" и ЛОМАЕТ любой зависимый регистр с реальными данными (найдено вживую:
  `UpdateDBCfg` отклонил такое изменение — "Недопустимое изменение регистра, в котором существуют
  записи"). Это уже исправлено в общем пайплайне `deploy_metadata_object` — не убирать этот фикс.
- **"Объект существует" = файл на диске И зарегистрирован в `Configuration.xml` — НЕ только файл**
  (см. `deploy_metadata_object`, #43). Осиротевший файл объекта (остался в дампе даже после удаления
  из конфигурации в Конфигураторе) обманывал старую проверку `not obj_xml_path.exists()` — тег
  регистрации в `Configuration.xml` никогда не добавлялся заново, `LoadConfigFromFiles`/`UpdateDBCfg`
  отчитывались успехом, но по факту это был no-op. Исправлено — `created` теперь проверяет ОБА
  условия, регистрация тега чинится идемпотентно ВСЕГДА, не только при `created=True`.
- **`kill_sessions` теперь распознаёт зависшие DESIGNER-вызовы (`/LoadConfigFromFiles`/
  `/UpdateDBCfg`/`/DumpConfigToFiles`) как СВОЮ автоматизацию, не интерактивную сессию человека**
  (см. `sessions._is_automation_process`, #44) — раньше такой зависший процесс попадал в
  `skipped_interactive`, приходилось убивать вручную через `taskkill /PID`.
- **`taskkill /PID N /F` через Bash (Git Bash) может НЕ сработать** — MSYS конвертирует `/PID` в
  путь (`C:/Program Files/Git/PID`). Используйте PowerShell для `taskkill`, не Bash.
- **Неудачный `UpdateDBCfg` НЕ откатывает то, что уже сделал `LoadConfigFromFiles`** (#42) —
  конфигурация (то, что читает `DumpConfigToFiles`) и реальная структура базы могут разойтись после
  отклонённого обновления. Признак — 1С показывает диалог "Конфигурация базы данных не соответствует
  сохранённой. Продолжить?" при следующем открытии — ловится `screenshot_1c_window`.
- **Ложное "зависание" ≠ реальный стоп на диалоге.** Легитимно медленные `DumpConfigToFiles`/
  `RunUnitTests` на тяжёлой конфигурации (минуты) дважды принимались за зависший диалог. Не
  угадывать по времени — `screenshot_1c_window(ib_connection)` покажет факт: диалог или прогресс.
- **`ib_connection` без/с НЕВЕРНЫМ `Usr=`** — оба варианта вешают интерактивный диалог логина
  headless-вызова НАВСЕГДА (не только полное отсутствие `Usr=`, но и неполное/неточное значение,
  например фамилия вместо полного отображаемого имени). Нужен ТОЧНЫЙ логин — см. `list_ib_users()`.
- **PowerShell через Desktop Commander start_process:** для запуска `"путь с пробелами" аргументы`
  использовать `& "путь" аргументы`, не `cmd /c "путь" аргументы` (ломает кавычки на длинных путях).

## Модель-фиксер (решено для роли фикса, НЕ пересматривать для неё)
Qwen2.5-Coder-7B Q4_K_M, LM Studio `:1235`, контекст ~4096 — под роль точечного фикса сниппета
(`heal_module`/`fix_snippet`) этого достаточно, не трогать. НЕ брать гибридные MoE-модели
(Gated DeltaNet) — llama.cpp не переиспользует их KV-кэш → зависание. Смена модели без правки
кода — `get_model()` берёт то, что загружено в LM Studio.

**Уточнение пользователя (#38):** контекст ~4096 — это НЕ жёсткий лимит модели, а текущая
настройка LM Studio под роль фикса. На RTX 3070 (мин. 8ГБ VRAM, без RAM-оффлоада) контекст той
же модели реально можно поднять до ~32К (проверено вживую, см. ниже — на 40К начинались проблемы,
похоже на offload в RAM).

**УСТАРЕЛО, ОПРОВЕРГНУТО ЖИВЬЮ (#54):** здесь раньше стояла заметка "гонять две модели
параллельно — плохая идея, не добавлять вторую (например embedding-модель)" — это оказалось
НЕВЕРНО. В #54 embeddinggemma-300M (~0.3ГБ) реально запущена ОДНОВРЕМЕННО с Qwen2.5-Coder-7B
(~4.5-5ГБ) в ОДНОМ инстансе LM Studio при контексте фиксера 32К — вместе ~8000/8192МБ VRAM
(впритык, но работает), `search_reference_semantic` подтверждён живьём и работает отлично.
Вывод: ДВЕ маленькие/средние модели одновременно — ОК, если суммарно укладываются в VRAM с
запасом на KV-кэш; именно РОСТ КОНТЕКСТА (не вторая модель сама по себе) съедает основную часть
свободной памяти — это и есть реальный лимитирующий фактор, не количество моделей.
